Ghidra 가 거부하므로 점 없는 심볼릭 링크로 연다), 실제 DB 조회, AX 실측(사용자 맥, 백그라운드). 상한 2시간.

## 1. 방 공지

- 출처(정적): `FCChatRoomNoticeController::noticeWithChatRoom:` 는 방의 `moimMeta`(톡게시판 공지)가 있으면 그것을, 없으면 `notice`(레거시)를
  쓴다. 공지 본문은 서버의 톡게시판 글이고, 로컬에는 미리보기만 있다.
- DB:
  - `NTChatMeta` type 1 `content`/`noticeText`: 최대 100자.
  - 공지 메시지 `NTChatMessage.type = 24` 의 attachment `os[t=1].ct` 와 `jct`(리치 텍스트 JSON) 둘 다 **최대 약 500자**(300건 실측, 220건이 정확히 500자 = 잘림).
- 화면:
  - 채팅창 상단 공지 배너 = `AXImage`(desc `chatroom icon noti` / `chatroom icon noti dark`) + id 없는 `AXStaticText`(약 94~100자, 미리보기) — AX 동작 없음.
  - 배너를 **실제 마우스로 클릭**하면(카톡이 1~2초 앞으로 옴) 제목 없는 창 `_NS:17` 이 열린다: 방 이름 텍스트, 탭 버튼들(스크롤 영역), 글 목록 `AXTable`.
    **실측 확인(2026-11-03 오후)**: 클릭하면 `_NS:17` 창이 '상세보기'로 열리고 `AXScrollArea _NS:141 > AXTable _NS:95 > AXRow > AXCell` 안에
    작성자 `AXStaticText _NS:41`, 시각·구분 `AXStaticText _NS:57`(예: `23시간 전 ・ 공지`), **전문 `AXTextArea`(id 없음, 974자 실측 — DB 는 500자)**,
    본문 링크 `AXLink` 들, 링크 미리보기 텍스트가 있다. 같은 창에 댓글 입력칸 `AXTextArea _NS:27` 과 `등록` 버튼(`_NS:68`)이 있으므로
    **절대 입력·클릭하지 않는다.** 읽은 뒤 창을 닫는다.
- **로컬 DB의 공지 행(2026-11-04 조사)**:
  - 공지 행은 늦게 들어올 수 있다. `not_found`였던 방 5곳 중 4곳에 나중에 type 24 행이 생겼고, 확인한 2곳의 행은 rowid상 이후 메시지보다 뒤에 삽입됐다. 실측 1건(2026-11-04)에서 공지 행이 없던 방을 kkt로 열자 같은 실행 안에 type 24 행이 생겼다. 방을 열 때 채워진다는 근거지만 1건뿐이다.
  - `type`에 0x4000(16384)이 더해진 행이 있다(공지는 16408, 글은 16385). node-kakao의 `DELETED_MESSAGE_OFFSET` 기준으로 삭제된 메시지이며, 앱 자체에서의 확인은 **미확인**이다. 행과 attachment 본문은 남아 있다.
  - 공지 메시지가 삭제 표시돼도 화면의 공지는 남아 있을 수 있다. 관찰한 방에서 16408 행 본문과 화면 공지의 상품이 같았다.
  - DB 행과 화면 공지의 본문이 500자 안에서도 다를 수 있다(2026-11-04 실측 2방). type 16408 방과 type 24 방 모두 앞부분은 같고 뒤쪽 항목만 바뀌거나 추가돼 있었다. 공지를 수정하면 DB 행이 갱신되지 않는 것으로 보이지만 수정 이력을 직접 본 것은 아니므로 **미확인**이다. 이 경우 490 미만의 `source: database` 결과도 화면과 다를 수 있다.
- **구현 기준(2026-11-06 변경)**: (1) 공지 길이와 상관없이 배너 클릭 → `_NS:17` 창의 표에서 전문을 읽는다(`source: screen`) — 카카오톡이 잠깐 앞으로 올 수 있다. (2) 실패하면 DB type 24 최신 공지 본문(≤500 UTF-16 코드 단위) + `source: truncated`, `truncated: true`. (3) DB에 공지 행이 없으면 배너가 없을 때 `not_found`, 화면 경로가 막히면 그 사유로 실패한다.
- **수정 신호 조사(2026-11-06, 수정 전후 비교는 안 함)**: 공지 메시지 1,184건의 `revision`은 모두 0이고, `NTChatLogMeta`의 공지 행 항목은 반응뿐이며, 첨부 `version`은 앱 버전, `extra`는 `byHost`뿐이다. `NTChatMeta` type 1은 공지 메시지와 비교된 9개 방 모두 공지 메시지보다 새롭지 않았다.
  `_NS:17` 창의 표에서 전문을 읽는다(`source: screen`) — 카카오톡이 잠깐 앞으로 올 수 있다. (3) 실패하면 DB 본문 + `source: truncated`, `truncated: true`. (4) 최신 공지가 삭제 표시면 길이와 상관없이 (2)를 시도한다. (5) DB에 공지 행이 없어도 (2)를 시도하고, 배너가 없으면 `not_found`, 화면 경로가 막히면 그 사유로 실패한다.

## 2. 채팅 목록 검색

- 검색칸(`AXTextField`)은 평소에 **없다.** 메인 창의 `AXButton`(desc `검색`, 동작 목록은 비어 있지만 `AXPress` 가 동작)을 누르면 생기고,
  다시 누르면 사라진다. 백그라운드에서 동작, 포커스 변화 없음(실측).
  → 검색칸 부재를 그대로 실패로 처리하면 화면에 보이는 약 13개 방 밖의 방은 `not_found`가 된다(실측 대상의 가상 이름: `일반방`, `미션방`).
  → kkt는 검색칸이 없으면 검색 버튼을 눌러 열고, 끝나면 입력을 지우고 버튼을 다시 눌러 닫는다(원래 상태가 "없음"이었을 때).
- 이름을 입력하면 결과가 같은 표(`_NS:63`)에 그려진다(AXChildren 2, 보이는 행 1).
- 입력 후에는 키 포커스가 검색칸에 남아 pid 로 보낸 Return 이 행을 열지 못한다(`automation_failed`). **표에 `AXFocused=true` 를 준 뒤** Return 을
  보내면 방이 열린다(실측).
- 표: `AXChildren` 1,385행 vs `AXVisibleRows` 13행(셀이 있는 것은 보이는 행뿐). 전체 순회 6~9초, 보이는 행 0.008초.

## 5. 사진 붙여넣기와 포커스 (2026-11-04)

- 입력칸의 `paste:` 본문(`FSChatInputTextView`)은 활성 상태를 직접 검사하지 않고, 일반 클립보드의 파일 URL을 읽어 `sendFilesAt:comments:skipValidCheck:showTransConfirm:silence:`로 넘긴다(정적 분석). ObjC 메서드는 공용 연결 코드로 넘어가는 얇은 진입점이라 구현 주소는 진입부 어셈블리에서 찾아야 한다. 파일 1개와 여러 개는 다른 분기를 탄다.
- 공유 확장(`kakaoshare`)은 대상 선택 창을 띄우는 함수 안에서 `activateIgnoringOtherApps:`를 호출한다. `AppDelegate`에 `application:openFiles:` 구현은 없고 문서 타입 등록도 없다(정적 분석).
- 비활성 상태에서는 `postToPid` Cmd+V, `편집 > 붙여넣기` AXPress, 창의 AXMain·AXFocused 설정 모두 시트가 뜨지 않았다(실측). 이때 메뉴 항목은 `enabled=0`, 창의 `AXFocused`는 0이다.
- `SLPSPostEventRecordTo`로 창 키 레코드만 보내도 시트가 뜨지 않았다(실측). 포커스 획득 레코드(`[0x08]=0x0d`, `[0x8a]=1`)를 함께 보내면 앞 앱은 그대로이고 카톡의 AX `frontmost`만 1이 되며, `postToPid` Cmd+V로 시트가 0.5초 안에 뜬다(실측, macOS 27.0.1). 해제 레코드(`[0x8a]=2`)를 보내면 `frontmost`가 0으로 돌아온다. 이 방식의 레코드 구성은 yabai를 참고했다. 비공개 API이므로 OS 업데이트 때 다시 확인한다.
- 포커스 획득 레코드만 보내도 시트가 뜨지 않으므로 두 레코드가 모두 필요하다(실측). 게다가 이 상태로 채팅 창을 닫자 이후 `postToPid` 키가 메인 창에 전달되지 않아 방 열기가 `automation_failed`·`not_found`로 실패했다. 메인 창에 포커스→키 창→해제 레코드를 보내자 복구됐다(실측 1회). 두 레코드를 함께 보낸 전송 뒤에는 이 증상이 없었다.
- 최소화된 메인 창은 AX 목록에 남지만 키 입력이 전달되지 않아 방 열기가 `automation_failed`로 실패한다. `AXMinimized`만 풀어도 실패가 이어진다. `창 > 채팅` 메뉴를 AXPress로 누르면 최소화·닫힘 상태 모두 앞 앱을 바꾸지 않고 창이 나타나고 키 입력도 정상이 된다. 창은 앞 앱 바로 아래에 놓인다(실측, 2026-11-04).
- 백그라운드 사진 전송 중 글+사진 1회가 시트를 띄우지 못해 전면 경로로 전환됐다. 같은 조건을 6회 반복했을 때는 재현되지 않아 원인은 **미확인**이다.
- `kkt send --image`로 나와의 채팅 1장·2장·글+사진, 그룹방 1장·2장(3회)을 보냈고 모두 `imageRoute: background`, 전송 뒤 방 열기와 글 전송도 정상이었다(실측, 2026-11-04).

- 번들 ID가 없는 앱(qemu 에뮬레이터)은 `open -b`로 되돌릴 수 없다. `NSRunningApplication.activate()`는 `true`를 돌려주지만 앞 앱이 바뀌지 않았고(실측 2회), `_SLPSSetFrontProcessWithOptions`(옵션 0x200)는 바뀌었다(실측 3회, macOS 27.0.1). 비공개 API이므로 OS 업데이트 때 다시 확인한다.

## 6. 기타 관찰

- 관찰한 환경에서는 채팅방이 화면에 그려질 때 링크 미리보기(`universalScrapData`)를 받아 왔다. 모든 수신 조건을 확인한 것은 아니다.
- 카톡이 닫힌 메인 창을 `open -g -b com.kakao.KakaoTalkMac` 으로 다시 띄우면 1~1.5초 뒤 스스로 활성화한다. 그래서 재오픈 때는 최대 2초 기다린 뒤 포커스를 복원한다.
